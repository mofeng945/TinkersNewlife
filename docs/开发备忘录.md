## 〇、总览：两大内容路线

| 内容类型 | 走匠魂工具链？ | 载体 |
|---|---|---|
| 术式（technique） | 是（占用咒力核心的 technique 槽） | `BaseTechnique` 单例 + 空壳 Trait modifier + crystal 配方 |
| 领域（domain） | 是（占用咒力核心的 domain 槽） | `BaseDomain` 子类 + 空壳 Trait modifier + crystal 配方 |
| 咒具（天逆鉾/杜兰达尔） | **否**（原版剑逻辑） | `CursedToolItem`（SwordItem 子类） |
| 模块化装备（咒力核心/魔杖/悠悠球/飞剑/战镰/驯龙杖/噤默手套） | 是 | `ModifiableItem` + `ToolDefinition` + parts/patterns |
| 强化特性（modifier/trait） | 是 | `StaticModifier` 注册 |

咒力核心（Curse Core）是术式/领域系统的中枢：佩戴在 curios `curse_core` 槽，自带槽位
`domain:1 + technique:1 + defense:2 + upgrades:3`，其 tool_definition 见
`src/main/resources/data/tinkersnewlife/tinkering/tool_definitions/curse_core.json`。

## ★★ 铁律：词条/特性效果一律兼容任意实体（玩家、诡厄仆从、怪物、召唤物……）

> 2026-09 起生效（先例：仆从用匠魂近战放宽 子路A、仆从弓 A+B+C、仆从穿盔甲规则 35）。

- **判定对象用 `LivingEntity`，禁止默认 `instanceof Player` 拦截**。穿戴者/攻击者/受害者/击杀者
  都可能是非玩家：穿上匠魂盔甲的 goety 仆从、拿匠魂武器的怪物、被召唤物杀死的目标等。
- 「特性」包括：材料 trait / 强化 modifier 的被动、反伤、击杀成长、自动修复等一切"穿/拿就生效"
  的效果；以及攻击类命中效果（攻击者放宽，已按 子路A 处理）。
- **只有本质绑定玩家交互的能力才保留 Player 限定**：按键/点击（PlayerInteractEvent、按键包）、
  GUI/菜单、客户端渲染、经验等级/玩家背包/灵魂槽等玩家特有资源。灵魂消耗类对仆从的规则：
  **扣主人的灵魂**（`GoetyBridge.getServantOwner` → Player；主人非玩家/无主/灵魂不足则不触发）。
- 新增任何 modifier/trait 时按此默认实现：先问"这个效果如果穿在骷髅仆从/拿在僵尸仆从身上
  应不应该生效"，应生效就不要写 Player 检查；需要消耗玩家资源的，用"玩家扣自己 / 非玩家扣主人"
  的统一模式（参考 `CursedAdrenalineHandler.resolveSoulSource`、`SoulRepairHandler.onServantTick`）。

## 一、新增一个术式（technique）

### 概念
- **Technique 单例**（如 `SkyManipulationTechnique.INSTANCE`）：真正的术式逻辑，继承 `BaseTechnique`，构造时 `super(Modifiers.XXX.getId())` 绑定自己的 modifier id。
- **Trait 空壳**（如 `SkyManipulationTrait extends Modifier`）：几乎无逻辑，只是"核心上的术式标记"，让术式能装进咒力核心 technique 槽、被切换/释放。
- 按键流程：`TechniqueHandler` 扫描核心上所有已注册术式 → 玩家切换选中 → 按下/松开/反转(F)调用选中 technique 的钩子（`PacketUseTechnique`/`PacketUseReverseTechnique` → `TechniqueHandler.onKeyPress/onReverseKeyPress...`）。

### 新增步骤（8 步）
1. **写 Trait 空壳** `content/modifier/XxxTrait.java`：
   ```java
   public class XxxTrait extends Modifier { }   // 纯标记，逻辑在 Technique 单例
   ```
2. **在 `content/Modifiers.java` 注册**（照 KaiTrait）：
   ```java
   public static final StaticModifier<XxxTrait> XXX =
       MODIFIERS.register("xxx", XxxTrait::new);
   ```
3. **写 Technique 单例** `content/curse/technique/XxxTechnique.java extends BaseTechnique`：
   ```java
   public final class XxxTechnique extends BaseTechnique {
       public static final XxxTechnique INSTANCE = new XxxTechnique();
       private XxxTechnique() { super(Modifiers.XXX.getId()); }
       // 即时型：覆写 onCast(player, target)
       // 近身限定：覆写 isTargetInRange（如捌 3 格内）
       // 蓄力型（灶·开范式）：onKeyPress 换手蓄力 / onKeyRelease 恢复+发射
       // 蓄力型（苍·赫范式）：状态机 onKeyPress/onKeyRelease，F 反转合成茈
       // 伤害型务必在 onCast 里走 CurseCoreTraitHelper.applyCurseCoreTraits/afterCurseCoreHit
   }
   ```
4. **在 `TinkersNewlife.java` 构造器登记**：`TechniqueHandler.register(XxxTechnique.INSTANCE);`
   → **crystal（镶嵌）/salvage（剥离返还槽）/extract（萃取成水晶）配方与墨默商人货架全部自动派生**，无需另写。
5. **清理与每 tick 驱动（按需）**：蓄力/操控状态挂进 `TechniqueHandler.onPlayerLoggedOut/onPlayerDeath`；每 tick 服务端逻辑挂 `TinkersNewlife.ForgeEvents.onServerTick`。
6. **资源**：
   - 图标 `assets/tinkersnewlife/textures/gui/modifiers/<id>.png`
   - `assets/tinkersnewlife/tinkering/modifier_icons.json` 追加
     `"tinkersnewlife:<id>": "tinkersnewlife:gui/modifiers/<id>"`
   - `assets/tinkersnewlife/lang/zh_cn.json` 三键：`modifier.tinkersnewlife.<id>`（名称）、
     `.flavor`、`.description`（名称键同时用于切换提示与领域标题）
7. **advancement**：`data/tinkersnewlife/advancements/techniques/<id>.json`（`{"criteria":{"unlock":{"trigger":"minecraft:impossible"}}}`）
   + `content/curse/TechniqueAdvancementHandler.java` 静态块
   `put(Modifiers.XXX.getId(), "techniques/<id>")`（照 kai）。
8. **remove_blacklist**：`data/tconstruct/tinkering/tags/modifiers/remove_blacklist.json` 追加
   `"tinkersnewlife:<id>"`（防被普通途径移除，只能走萃取/配方）。

**可选**：加入 `CurseCoreRitualHandler.generateCurseCore` 的术式数组，让生成仪式可随机给到。

### 获取途径（玩家侧）
- **墨默商人**（`MomoMerchant.ensureOffers`）每天随机上架 2 个术式水晶
  （`ModifierCrystalItem.withModifier(techniqueId)`，40-60 格赫罗斯残骸）。
- **咒力核心生成仪式**（`CurseCoreRitualHandler`）产出的核心随机附 1 术式 + 1 领域。
- 用带术式 modifier 的水晶在工匠站给核心"镶嵌"（扣 1 technique 槽）；剥离走萃取返还槽。

### 蓄力/反转样板
- 蓄力换手型：`ZaoKaiTechnique`（灶·开，换 FLAME_ARROW_ITEM 手持蓄力、松手发射）。
- 状态机型：`WuliangCangTechnique`（苍/赫/茈，F 反转键在蓄力中合成茈）。
- 反转语义自定：`SkyManipulationTechnique`、`WuWeiTechnique`、`ReverseCursedTechnique` 等覆写 onReverseKeyPress。

## 二、新增一个领域（domain）

### 概念
- **Domain 子类** `extends BaseDomain`：构造 `(UUID owner, Vec3 center, int radius, double curseCostPerSecond)`，
  center=展开瞬间玩家位置（球心），radius 惯例 = `CursePowerHelper.getCurseOutputLevel(player)*5`，
  消耗惯例 = `radius × 每秒每半径消耗`（坐杀搏徒 ×20、御厨子 ×40、无量空处 ×80）。
- **Trait 空壳** 占 domain 槽（核心固定只有 1 个领域槽）。
- 领域工厂 `static XxxDomain tryCreate(ServerPlayer)`：校验条件，不满足返回 null（已在工厂内提示）。
- 展开后：视觉黑球实体 + 隐形阻挡墙 + 困锁 + 每 tick 消耗/逻辑 + 对抗，全部由 BaseDomain/DomainRegistry 通用外壳接管。

### 新增步骤（7 步）
1. **Trait 空壳** `content/modifier/XxxDomainTrait.java extends Modifier`。
2. **`content/Modifiers.java`** 注册 `StaticModifier`。
3. **领域类** `content/curse/domain/XxxDomain.java extends BaseDomain`：
   - 抽象钩子必实现：`getDomainNameKey()` → `"modifier.tinkersnewlife.<id>"`（展开大标题）；
     `isValid(player)` → 核心上仍有该 modifier（否则领域被破坏+熔断）。
   - 可选覆写：`onOpen` / `onTick(player, serverTickCount)` / `onClose(player, msgKey)` /
     `onClashStart/onClashEnd`。**计时用 `server.getTickCount()`，别用 getGameTime**（踩坑）。
   - 效果实现参考：`FuMoYuChuZiDomain`（AABB 圈选 + CurseCoreTraitHelper 让领域伤害带核心材料特性）。
4. **登记** `TinkersNewlife.java`（150-153 区块）：
   ```java
   DomainRegistry.registerDomain(Modifiers.XXX_DOMAIN.getId(), XxxDomain::tryCreate);
   ```
   → V 键展开、crystal/salvage 配方自动生效，**无其它注册点**。
5. **资源**：图标 png + `modifier_icons.json` + lang 三键（同术式）。
6. **advancement**：`data/tinkersnewlife/advancements/domains/<id>.json` +
   `TechniqueAdvancementHandler` 登记 `put(..., "domains/<id>")`。
7. **remove_blacklist.json** 追加 id。

**可选**：加入 `CurseCoreRitualHandler.generateCurseCore` 的 domains 数组（仪式随机给）。

### 现有领域参考
`ZuoShaBoTuDomain`（坐杀搏徒）、`WuLiangKongChuDomain`（无量空处）、`FuMoYuChuZiDomain`（伏魔御厨子）。
通用设施（新领域无需注册）：阻挡方块 `ModBlocks.DOMAIN_BARRIER`、视觉实体 `ModEntities.DOMAIN_VISUAL`（渲染注册于 `ClientEventHandler`）。

## 三、咒具与模块化装备制作

### 关键区分（勿混）
- **咒具（天逆鉾/狱门疆/杜兰达尔剑）= 原版剑**，`CursedToolItem extends SwordItem`：无限耐久、命中亡灵 +6、
  `ignoresInfinity()` 默认 false（天逆鉾覆写 true 穿无下限）。**不是匠魂工具**。
- **匠魂工具（咒力核心/魔杖/悠悠球/飞剑/战镰/驯龙杖/噤默手套）= `ModifiableItem` + `ToolDefinition`**，走工匠站全流程。
- 术式/领域 modifier 多为**空标记类**，逻辑在 Technique/Domain 单例与事件 Handler。
- 核心**没有自定义 GUI**："装术式/剥离"UI = 匠魂工匠站配方系统（crystal/salvage/extract），不是本模组 Screen。

### A. 新增自定义物品（N 步）
1. `content/item/` 新建 Item 子类（咒具 `extends CursedToolItem`，Tier 匿名类内联）。
2. `content/ModItems.java`：`ITEMS.register("id", () -> new X(new Item.Properties()...))`
   （**注册表冻结：只许在 supplier 里 new**；勿运行时补注册）。
3. 方块物品/药水/实体/声音各进对应 DeferredRegister（ModBlocks/ModEffects/...）。
4. 创造栏：`ModCreativeTabs.displayItems` 里 `output.accept(...)`；
   匠魂工具用 `addAllToolVariants(output, definition, item, partCount)`，部件 `addAllPartVariants`。
5. 资源：`assets/.../models/item/<id>.json` + `textures/item/<id>.png`；lang `item.tinkersnewlife.<id>`（描述 `.desc`）。
6. 行为/掉落：`content/handler/*.java` 事件或 loot modifier（如 `DurandalConversionHandler`）。

### B. 新增匠魂工具（含自带 modifier / 挂核心槽）
1. item 类 `extends ModifiableItem`，静态 `ToolDefinition.create(rl("<tool>"))`；饰品实现 `ICurioItem`。
2. `ModItems` 注册工具 item + 必要 ToolPartItem 部件/铸模铸件。
3. `data/.../tinkering/tool_definitions/<tool>.json`：parts + `modifier_slots` + 自带 `traits`
   （咒力核心：`domain:1 technique:1 defense:2 upgrades:3` + 自带 curse_output/curse_total 1 级）。
   新槽类型需在 `TinkersNewlife()` 构造器 `SlotType.getOrCreate("xxx")`。
4. 部件数据：`tinkering/parts/<part>.json`（stat_type）+ 图标/模型。
5. `tinkering/station_layouts/<tool>.json` 定工匠站 GUI（tool_slot/input_slots）。
6. 配方：`recipes/tools/building/<tool>.json`；多部件还需 parts builder/cast + smeltery/casts 与 casts 标签（模板 dragon_core/yo_yo）。
7. 打标签：`data/tconstruct/tags/items/modifiable/...`（melee/primary、weapon 等）；不可拆解加 `unsalvageable.json`。
8. curios 槽：`ModCurios.enqueueIMC` + `data/curios/tags/items/<slot>.json`；`canEquip` 校验。
9. 特殊添加通道（咒力核心术式/领域）：`recipes/modifiers/crystal/<kind>.json`（crystal_modifier 镶嵌扣槽）
   + `salvage/<kind>.json`（modifier_salvage 剥离退槽）+ 可选 `extract/<kind>.json`（剥离成水晶转移）。
   新增术式/领域**自动被覆盖**（加载时遍历 TechniqueHandler/DomainRegistry）。

### C. 新增仪式配方（多方块脚本式，参考 CurseCoreRitualHandler）
1. `content/curse/ritual/XxxRitualHandler.java`，`@EventBusSubscriber(FORGE)`，
   静态 `Map<BlockPos,RitualData>` 存进行中仪式。
2. 触发：`RightClickBlock`（空手/特定方块）或 ServerTick 扫 ItemEntity。
3. 校验：结构方块计数/偏移硬编码；流体走 `IFluidHandler` capability；必要时月相/亮度/露天。
4. 演出：ServerTick(END) 驱动 `ticksLeft--` + 粒子（光束/BlockParticleOption 连线）。
5. 完成：`handler.drain` 扣流体、`giveExperienceLevels` 扣经验、`addFreshEntity(new ItemEntity(...))`；

## 四、咒力核心生成仪式（快速回顾）
- 结构：格赫罗斯矿石下放焦黑/焦褐材料量器（存 ≥864mB=6 锭流体），矿石四周隔 1 格放石/铁/金/钻石块。
- 触发：空手右键 GHELOTH_ORE；5 秒后消耗流体 + 50 级经验 → 生成核心
  （材料=流体经 material_fluid 反查；咒力总量/输出 1~5；随机 1 术式 + 1 领域；30% 额外术式槽 ≤3）。
- 熔化回收：丢冶炼炉 → `auto_material_melting` 配方按 `recipes/materials/<mat>_material_fluid.json` 还原流体。
- 术式水晶获取：墨默商人每日货架随机 2 个（`ModifierCrystalItem.withModifier`）；领域靠仪式/剥离转移。

## 五、常用工具与引用速查

### 咒力（`content/curse/CursePowerHelper.java`）
- 核心查找：`findEquippedCurseCore(player)`（curios `curse_core` 槽）；`getModifierLevel(core, id)`。
- 等级/亲和：`getCurseOutputLevel(player)`（含天与咒缚 +1 / 咒种寄生 -1）、`getCurseTotalLevel`、
  `getCurseAffinity(player)`（饰品之和 + 临时 + 束缚加成 - 寄生60）。
- 数值/支付：`getMaxCurse`（总量×(输出+亲和/10)×500）、`getCurse/setCurse/addCurse/spendCurse`；
  `payCurseWithSoulFallback(player, cost)`（结界碎片 1枚=25 → 咒力 → 诡厄灵魂能量 1:3，返回 0/1/-1）；
  `countBoundaryFragments` / `consumeBoundaryFragments`。
- 状态：`isCurseInfinite` / `applyBurnout|isBurnout|getBurnoutRemainingSeconds` /
  `applySeal|isSealed|getSealedRemainingSeconds`。

### 术式（`BaseTechnique` 内置）
- `tryUse(player)` 模板：熔断检查 → 扣费 → 视线索敌(16格) → 距离校验 → `onCast`。
- `getCost` / `payCost` / `findTarget` / `isTargetInRange` / `onCast`。
- `computeBaseDamage`（共享成长伤害）、`amplifyTechniqueDamage`（模块化魔杖增幅）、`spawnSlashParticles`。
- 伤害型术式务必调用 `CurseCoreTraitHelper.applyCurseCoreTraits/afterCurseCoreHit`
  （`content/curse/CurseCoreTraitHelper.java`，手动触发核心材料特性）。

### 领域（`content/curse/domain/`）
- `BaseDomain`：`buildBarrier/removeBarrier/removeBarrierOverlap`（墙）、`spendCurse`（每秒扣费+灵魂兜底）、
  `clampEntities`（困锁，每 5 tick）、`clashOpponent/clashCostMultiplier`（对抗）、
  `getBarrierPositions`（供破域掉落碎片）；子类抽象钩子 `getDomainNameKey()` / `isValid(player)`，
  可选 `onOpen/onTick(player, serverTickCount)/onClose(player,msgKey)/onClashStart/onClashEnd`。

      生物封印走 NBT 不受影响。
    - **处置**：用户接受弹窗（一次性确认，点后 confirmedExperimentalSettings=1 不再弹），
      维度 json 保持原样（勿再动）。若将来要消除：唯一办法是彻底移除维度定义（数据包或代码
      注册都会进创建流程注册表；Forge 1.20.1 RegisterEvent 无 getRegistryAccess，代码注册

    - ① **根因**：手写的 `tinkersnewlife.refmap.json` 用的是**点号类名**

      `irons_spellbooks:alchemist_cauldron_empty`（玻璃瓶 + **流体**）产出的物品，
      它的 `ingredients` 只有一个玻璃瓶 → 我按"配方物品原料"估值时，五档墨水全都只值一个玻璃瓶，
      于是不同品质的卷轴（用不同墨水做）价格一模一样。
      **价值藏在流体链里**（`alchemist_cauldron_brew`：rare_ink 流体 + 金锭 → epic_ink 流体 …），
      而通用配方 API 拿不到"流体投入"。
    - 修法三件套：
      ① **品质词加成**（`DEFAULT_TIER_BONUS`，配置 `tier_bonus` 可覆盖/追加）：
         物品 id 里出现 `uncommon=6 / rare=14 / epic=30 / legendary=60 / mythic=90 / divine=90 /
         supreme=120 / ultimate=120` 任一 → 加对应分（多词取最高，不叠加）。
         这正好对上 `common_ink / uncommon_ink / rare_ink / epic_ink / legendary_ink` 这种命名。
      ② **手动指定价值**（配置 `value_overrides`）：`物品id=分数` / 通配符 `*_ink=120` / 标签 `#forge:gems=25`，
         命中即**替代**计算结果，专治公式猜不到的怪物品。
      ③ **原料价值递归不再打 0.5 折**、深度 2→3、并加上限 80：
         原来的折损会让多级合成链上的价值迅速归零（高级墨水传不到卷轴），现在全额传播 + 上限兜底。
    - 效果（倍率 10、亲和 0、输出 1 的估算）：
      * 普通墨水自身分 2 → 稀有 16 → 史诗 32 → 传奇 62（自身即 20~620 咒力，不能再白菜价拟造）；
      * 卷轴：普通卷轴原料项 ≈5 → 约 **460 咒力**；传奇卷轴原料项 ≈66 → 约 **910 咒力**（约 2 倍差距）。
    - 已构建部署到两个实例。
101. **构筑造价补上"无配方物品"（挖矿/采集/掉落）的价值 —— 三条获取难度代理**：
    - 问题：不少高价材料**根本没有配方**（钻石、下界之星、鞘翅、图腾、远古残骸…），
      配方链估值对它们完全失效 → 只能拿到"稀有度+非方块"两分，进而把下游产物也压低。
    - 修法：在自身分里加三条**获取难度代理**（都可配、都有上限，避免爆表）：
      ① **不可堆叠加成** `unique_item_bonus`（默认 8）：`getMaxStackSize() == 1` 的物品
         （鞘翅/图腾/三叉戟/盾牌…）几乎都是独特之物；
      ② **方块硬度代理** `hardness_cap`（默认 25）：`BlockItem` 取
         `defaultBlockState().getDestroySpeed(null,null)`，加分 = min(上限, 硬度/2)
         → 黑曜石 50→25、远古残骸 30→15、铁矿 3→1.5、泥土 0.5→0.25（自然拉开档次）；
      ③ **标签价值表** `tag_values`（含内置默认，合计受 `tag_value_cap`=60 限制）：
         `#forge:ores=12` `#forge:raw_materials=8` `#forge:ingots=10` `#forge:gems=25`
         `#forge:dusts=6` `#forge:nuggets=2` `#forge:storage_blocks=20` `#minecraft:coals=5`。
         这些**同时**作用在原料递归里，所以"用钻石做的剑"会因为钻石本身有价而整体抬价。
    - 现在的自身分 = 稀有度 + 材料/方块 + 攻击×4 + 护甲(防+韧)×3 + min(20,耐久/300)
      + 品质词(uncommon6…legendary60…) + 不可堆叠(8) + 硬度代理(≤25) + 标签价值(≤60)；
      再叠加 原料项×0.75 与 魔法功能项(40)，最后乘 max(0.25,1-亲和/100)×(1+输出×0.2)×cost_multiplier。
    - 已构建部署到两个实例。

## 备忘 109：构筑造价两处失真修复（神灵金属锭 1200+ vs 神灵金盔甲 200）

用户反馈：`goety_revelation:apocalyptium_ingot`（神灵金属锭）要 1200+ 咒力，但用它升级出来的
神灵金盔甲只要 200 咒力 —— 成品比原料便宜，明显不合理。定位到 `ConstructTechnique` 里两个独立 bug：

### Bug 1：`Recipe#getIngredients()` 是默认空实现

1.20.1 的 `Recipe#getIngredients()` **默认返回空表**（`NonNullList.create()`），
`SmithingTransformRecipe`（锻造台升级）**没有覆写它** —— 它的三个原料存在自己的
`template` / `base` / `addition` 字段里。结果：盔甲的"原料项"恒为 0，
造价只剩盔甲自身分（稀有度 + 护甲 + 耐久 ≈ 200 咒力），跟原材料完全脱钩。

修复（`describeRecipe`）：
- 先正常取 `recipe.getIngredients()`；**若为空**（或抛异常）就调 `reflectIngredients(recipe)` 兜底。
- `reflectIngredients` 沿类层次扫所有"像原料"的字段：类型是 `Ingredient` / `Ingredient[]` /
  泛型里带 `Ingredient` 的 `Collection`，逐个 `setAccessible(true)` 读出来解包。
- 字段列表按类缓存（`INGREDIENT_FIELDS`，`IdentityHashMap` 语义的 `HashMap<Class<?>, List<Field>>`），
  每轮不动点迭代不重复反射。

这样锻造台升级、以及其它"不覆写 getIngredients 的自定义配方类型"都能算到原料价值。

### Bug 2：多产物配方没除产出数量

`goety_revelation:apocalyptium_ingot` 是 `goety:ritual`（`ritual_type: goety:craft`）配方的产物：
**8 × `goety:dark_ingot` + 1 × `goety_revelation:ascension_halo`（激活物）→ 9 × 神灵金属锭**。

## 备忘 110：拟造末影之眼塞传送门框架 → 到期把"框架本身"炸没了

用户反馈：把拟造的末影之眼右键塞到末地传送门框架上，时间一到，**连框架一起碎了**。

### 根因：`useOn` 里的 setBlock 也会触发 `EntityPlaceEvent`

`ItemStack#useOn` → `ForgeHooks.onPlaceItemIntoWorld` 会打开 `Level#captureBlockSnapshots`
（源码：`ItemStack.java:245`、`ForgeHooks.java:568`），于是**任何 `useOn` 内部的 `setBlock` 都会被当成一次"放置"**
并在返回 `consumesAction()` 时触发 `BlockEvent.EntityPlaceEvent`（`ForgeEventFactory.onBlockPlace`）。

末影之眼正是这种：`EnderEyeItem#useOn` 把传送门框架的 `has_eye` 从 false 改成 true：
```java
level.setBlock(blockpos, blockstate.setValue(EndPortalFrameBlock.HAS_EYE, true), 2);
```
快照里"被替换的方块"就是**同一个末地传送门框架**。而老代码在 `onBlockPlaced` 里无条件按
`event.getPlacedBlock()` 记录，到期时判断 `current.getBlock() == 记录方块` —— 依旧是那个传送门框架，
所以成立 → `setBlock(AIR)` → **框架被删**。（顺带解释了为什么"眼"没了、框架也没了。）

> 注意：Forge 触发事件前会把物品堆的 count/NBT **还原成放置前**（`itemstack.setCount(size); setTag(nbt)`），
> 所以即便眼被 `shrink(1)` 消耗掉了，我们读手持物品时仍能拿到带 `KEY_TEMP_UNTIL` 的那份 —— 记录一定会生成。

### 修复：区分"凭空放下新方块"和"改宿主方块状态"

- `BlockSnapshot#getReplacedBlock()` 拿"放置前的旧状态"（`Level.setBlock` 在真正改方块**之前**建快照，见 `Level.java:210-212`）。
- `PlacedTempBlock` 增加 `previousState` 字段，`onBlockPlaced` 记录 `(放置后状态, 被替换旧状态)`。
- 到期逻辑改成两条路：
  1. `previousState` 为空/空气 → **整块收回**（原行为：容器先弹内容物 + 破坏音效 + SMOKE）。
  2. `previousState` 非空气 **且 `current == p.state`（状态精确相等）** → **只把旧状态撤回**，
     宿主方块原地保留（末影之眼到期 = 框架恢复成"没镶眼"，框架不碎）。
     `current != p.state` 说明后来被人动过，那就什么也不做。
- 顺带修好了另一类同源 bug：**锄头翻地**（泥土→耕地）、**打火石点火**、**斧头去皮**
  这些"改宿主状态"的拟造工具效果，旧代码同样会把宿主方块整个删掉。
- 又顺带支持了 `EntityMultiPlaceEvent`（门/床/高草一次改两格）：逐个快照记录，
  否则只删一半、另一半永远留着。它 `extends EntityPlaceEvent`，用 `instanceof` 分流，
  走 `getReplacedBlockSnapshots()` 里每格自己的 `(getCurrentBlock(), getReplacedBlock())`。

### 行为说明（可再调）

- 现在拟造末影之眼到期 → **框架保留、眼消失**（框架回到未镶眼状态）。
  之所以不退化成"眼永久保留"，是不想让临时拟造物白送一个永久激活的末地传送门。
  若希望"眼留在框架上不动"，把第 ② 分支整个去掉即可。

- 构建产物 `build/libs/tinkersnewlife-1.0.1.7.jar` = 4253911 字节。
- 本次只动 `ConstructTechnique` 的"拟造方块到期"这一条链路，未改造价/黑名单/掉落扫描。

## 备忘 112：十影调伏战 —— 主人打未调伏式神无伤害（"友军保护"误伤）

用户反馈：十影术法的**未调伏式神，主人打它完全没有伤害**，导致调伏战打不下去（调伏的唯一途径就是击败它）。

### 排查：模组里没有任何"禁止主人打式神"的硬拦截

把所有可能拦下"玩家近战攻击"的地方都过了一遍：
- `AttackEntityEvent` 的监听只有 StunHandler（罚站）、WuWeiHandler（变形/转变外放）、
  天逆鉾×2、游云、ex_pierce、缄默手套——都需要**特定物品/状态**，与式神无关；
- `LivingAttackEvent` 的 13 个监听全是装备/词条/效果触发，没有一个按"阵营"取消；
- 式神实体没有任何 `setInvulnerable` / `isInvulnerableTo` 覆写；
- `PuppetUtil.isAllyOf` 本来就特意写了"只有**已调伏**的式神才算队友，未调伏必须能被主人攻击"。

但确实找到了**三处"未调伏式神被当成友军"的真实缺陷**，全都会让主人的伤害消失：

1. **`CursedSpiritTechnique.goetyOwnerOf` 的盲扫反射（根因）**
   它按"公开方法名带 owner/master 且返回类型恰好是 `LivingEntity`"来猜 Goety 主人链。
   而 `TamableAnimal#getOwner()`（泛型擦除后正是 `LivingEntity`）会被命中——
   玉犬这类继承 `TamableAnimal` 的式神，还会额外生成 `getOwner(): ServerPlayer` 的**桥接方法**，
   于是"式神自己声明的主人"被当成了一条 Goety 主人链 →
   `isSpiritTeam(式神, 主人)` 变成 **true** → `PuppetUtil.isAllyOf` 判成友军 →
   `onMinionAttackAlly` 直接 `setCanceled(true)`；`onMinionTargetChange` 还会顺手把
   "未调伏式神锁定主人"也取消掉（它连主人都不会打）。
   **修**：`goetyOwnerOf` 先要求 `GoetyBridge.isGoetyServant(e)`（真的 Goety 仆从）才继续，
   优先用 `GoetyBridge.getServantOwner`，反射只作为仆从的兜底；
   并在 `isSpiritTeam` 开头加显式分支：`ShikigamiMob` → `已调伏 && 同主人` 才算同队。

2. **`ShikigamiBehavior.isFriendly`（AoE 阵营判定）**
   原来 `if (e == self || e == info.getOwner()) return true;`——**未调伏**时主人也被算友军，
   于是踏压/喷水/闪电这类 AoE 对主人完全不生效（近战能打到，AoE 打不到，观感像"友军"）。
   **修**：主人只在**已调伏**时算友军：`if (e == info.getOwner()) return info.getState().tamed;`

3. **三个领域的 `isFriendlyTo`**（断云平线／三重极躯／自闭圆顿裹）
   `owner.getUUID().equals(sm.getOwnerId())` 不看 `tamed` → 自己的**未调伏**式神在自家领域里
   也被当友军（不免伤/不转变）。
   **修**：加上 `sm.isTamed()`，与 1 的语义统一：未调伏 = 敌人。

### 兜底：调伏战保护（`ShikigamiHandler`）

上面的坑可能不止这几处（整合包里别的模组也可能有"友军保护"），所以再加一层兜底，
在**最低优先级**（其它监听都跑完之后）处理"主人打自己的未调伏式神"：

- `LivingAttackEvent`（LOWEST）：被取消 → **`setCanceled(false)`** 撤销，并打一条 WARN 日志
  （写明式神类型与攻击者）——如果还有别的东西在拦，这条日志就能把它暴露出来；
- `LivingHurtEvent` / `LivingDamageEvent`（LOWEST）：伤害被抹成 0 → 按攻击者攻击力（至少 1）恢复。

**两种"攻击者自身被惩罚"的情况不撤销**（那不是友军保护，撤销会破坏机制）：
投射咒法「静止」罚站（`StunHandler.isStunned`）、
伏诛赐死「亡灵有罪」攻击力归零（`ExecutionDomain.ATK_ZERO_UNTIL`）。

> 说明：这次没能复现用户的具体场景（静态排查没找到能拦住非 `TamableAnimal` 式神的代码），
> 因此采用"修掉全部已知误判 + 最低优先级兜底 + 日志取证"三管齐下；
> 若仍打不出伤害，日志里的 `[调伏战]` 行会指出拦截来源。

## 备忘 113：一批四个 bug（荡蕴平线含水方块 / 摘核心收术式 / 转变后仍可操控 / 拟造实体到期）

### 1. 荡蕴平线：含水方块（waterlogged）没有清除逻辑

**现象**：领域关闭后，台阶/楼梯/栅栏/珊瑚这类方块仍然含着水。

**根因**：注水后原版流体顺着扩散把"可含水方块"灌成 `waterlogged=true`，
而 `clearWater` 只处理真正的 `minecraft:water` 方块（BFS 也只在 `is(Blocks.WATER)` 上扩散），
含水方块既不在记录里、也不是水方块 → 永远留着。

**修**：`clearWater` 改为返回"被清掉的位置集合"；新增 `dryWaterlogged(level, cleared)`：
从「刚清掉的水位 + 当初记录的水位」出发，沿**含水方块**做 BFS（含水方块彼此也是连通的），
逐个把 `WATERLOGGED` 置回 false，只影响与领域水域连通的那一片，不误伤领域外/原本就含水的方块。

### 2. 摘下咒力核心没有解除持续性术式

**根因**：持续性/开关型术式（无限屏障、压力场、无限弹药、黑鸟操控、拟造物、变形本体……）
只在"领域关闭 / 死亡 / 登出"这些明确路径上收尾，**没有任何地方监听"核心被摘下"**。

**修**：`TechniqueHandler` 新增 `onPlayerTick`（每 10 tick 检查一次"佩戴核心指纹"= 物品 + 术式列表）：
- **核心没了** → `WuWeiHandler.endTransformPublic`（自己的变形本体，被他人转变不管）+
  `stopAllSustained`（全部持续性术式）+ 清空选中 + 同步客户端 + 动作栏提示；
- **换了核心** → `closeBorrowedSustained`（停掉新核心上没有的持续状态）+ 选中回退到新核心第一个术式。

用轮询而不是监听槽位：摘下核心的路径太多（背包移动/饰品栏/掉地/被清除/换核心），轮询才全覆盖。
领域不用管——`DomainRegistry` 每 tick 用 `isValid` 校验核心，自己会关。
新增语言键 `message.tinkersnewlife.technique.core_removed`（中/英）。

### 3. 可操控单位（傀儡操术 / 黑鸟操术）被无为转变后失去全部 AI

**根因**：`tryAttackReversal` 对生物目标一律"`discard()` 旧实体 → 生成新生物 → 挂玉犬式守护 AI"，
而这两个术式的操控链路是「**实体 id 绑相机 + 每 tick 输入包 → findActivePuppet/findActiveBird**」：
实体一删，输入包找不到目标、相机指向已删除实体 → 再也操控不了，看起来就是"失去所有 AI"。

**修**：对"**正被该玩家操控的单位**"改走 `transformControllableInPlace`（原地换形态）：

- **保留实体**——操控链路一根不断；只把形态写进持久数据 + 广播新增的 `PacketMobDisguise`
  （实体 UUID 为键，`StartTracking` 时给新来的玩家补发），客户端用**渲染代理**把这个实体画成目标生物
  （复用玩家伪装那套：`EntityRenderDispatcher` HEAD 拦截 + `WuWeiDisguiseRenderer.syncProxy`，
  后者参数从 `Player` 泛化成 `LivingEntity`）；
- **数值换成形态的**——生命上限/护甲/韧性/攻击按该玩家 `(1+亲和/100)×输出` 缩放写入属性；
  移速取形态速度但夹在原速 ±50% 内（操控手感不能因为换个形态就失控）；
  另外记一个「**形态攻击倍率**」= 形态基础攻击 / 基准 8（夹在 0.3~4.0），
  由操控单位自己的伤害公式乘算（**傀儡左击/自爆、雪傀儡雪球/自爆、黑鸟自爆**共 5 处接入）——
  因为这些单位的伤害是各自公式算的，光改 `ATTACK_DAMAGE` 属性没用。

`isPlayerControlled` 覆盖：正骑乘的坐骑（顺带覆盖骑鵺）、傀儡操术的傀儡（`PuppetGolemMob.puppetOwner()`）、
黑鸟操术的黑鸟（`getOwner()`）。

客户端"实体形态伪装"表用**带访问序淘汰**的 `LinkedHashMap`（上限 512）：
实体消失时客户端收不到通知，靠"最久未用先淘汰"兜底，避免表无限增长。

已知取舍：实体碰撞箱仍是原单位大小（`PuppetIronGolem` 等把 `getDimensions` 写死成原版尺寸），
所以"大傀儡变成鸡"时模型比碰撞箱小——属于观感问题，不影响操控与判定。

### 4. 拟造物召唤的实体（假人等）到期不消失

**根因**：拟造物到期清理只覆盖三类：玩家背包/容器里的物品、地上的 `ItemEntity`、放置的方块/部件。
**"用物品生成实体"**（假人、盔甲架、刷怪蛋……）走的是 `EntityPlaceEvent` 之外的路，没有任何跟踪。

**修**：右键瞬间给玩家周围 6 格的实体拍 **id 快照**（`watchEntitySpawn`，`RightClickBlock` 与
`RightClickItem` 都接），2 tick 后对比出"新出现的实体"，`markTempMob` 给它写入 `KEY_TEMP_UNTIL`
并入 `TRACKED_TEMP_MOBS`；服务端每 tick 检查到期 → 烟雾粒子 + `discard()`。
（与"右键改宿主方块状态"同一套快照思路，见备忘 110。）

## 备忘 114：静止效果定不住玩家（时序 + 客户端权威 两个根因）

用户反馈：静止效果（无量空处 / 胎藏遍野 / 十宝月宫殿 / 伏诛赐死 / 诅咒之言 / 弥虚葛笼自缚…）
挂上了，但玩家照样能走能跳。

### 根因：冻结逻辑的执行时机根本不对

原实现只有两处"定身"：

1. 服务端 `StunHandler.onServerTick`（`ServerTickEvent.END`）里 `player.xxa = 0; player.zza = 0;`
2. 客户端 `ClientEventHandler.onClientTick`（`ClientTickEvent.END`）里清 `player.input`

**两处都清不掉移动**：

- **1.20.1 的玩家移动是客户端权威的**：客户端自己算位移、自己发位置包，服务端写 `xxa/zza` 影响不到客户端，
  服务端只在 `ServerTickEvent.END` 清更是"移动早算完了"。
- 客户端那处也一样晚：`LocalPlayer#aiStep` 的顺序是
  ```
  input.tick(...)                             ← 每 tick 从键盘重新读输入
  ForgeHooksClient.onMovementInputUpdate(...) ← 本事件（之前没人用）
  跳跃/冲刺/使用物品逻辑 → travel()            ← 用 xxa/zza 结算位移
  ```
  而 `ClientTickEvent.END` 在**玩家 tick 之后**才跑，清掉的输入下一 tick 又被键盘重新读一遍 —— **"清了等于没清"**。

### 修复：改到正确的注入点 `MovementInputUpdateEvent`

新增 `ClientEventHandler.onMovementInputUpdate`：该事件正好在"读完键盘、还没结算移动"之间触发，
在这里把 `input.leftImpulse/forwardImpulse/jumping/shiftKeyDown` 清零 + 顺带清 `player.xxa/zza/jumping/sprinting`，
这一 tick 就真的走不动了。**同一个事件顺带修好了投射咒法「罚站」**——它原来也是放在
`ClientTickEvent.END` 清输入，同样无效（只是视角锁定掩盖了问题）。

其它配套（都按领域文档里承诺的"无法攻击/移动/使用物品/切换物品栏/打开背包"补齐）：

- 客户端：静止期间**锁住快捷栏槽位**（滚轮/数字键改了就锁回原槽）、
  关掉 `AbstractContainerScreen` 类界面（背包/箱子/curios；死亡/暂停等界面不动）；
- 客户端：`InteractionKeyMappingTriggered`（攻击/使用/丢弃）静止期间一律取消 —— 连挥手动画都没有；
- 服务端：玩家段改到 `TickEvent.PlayerTickEvent` 的 **START** 相位（否则同样是"马后炮"），
  继续负责关容器界面，并加了一层**兜底锚点**：静止期间若玩家"自己走开"超过 1 格就拉回原位
  （只对"没装本模组 / 作弊"的客户端生效；被击退/推挤、坐载具、泡水泡岩浆时重新锚定，
  保证"静止仍受物理影响"的设计不被破坏）。

### 顺带查出的第二个缺陷：两个领域只停了生物导航，没停 AI

`ExecutionDomain`（伏诛赐死）与 `QianheYingyiDomain`（嵌合影翳庭）给生物挂静止时只调了
`mob.getNavigation().stop()`，**没有调用 `StunHandler.onStunApplied(mob)`** ——
而生物侧的静止完全靠 `STUNNED_MOB_NOAI` 里登记的实体每 tick `setNoAi(true)`。
少了登记，生物只是"这一下停了脚"，AI 照常走位/攻击，静止对生物形同虚设。已补上（与其它领域一致）。
